Cursor shipped a 0day that doesn’t exploit a model. It doesn’t manipulate a prompt. It doesn’t even require a jailbreak. It simply executes a file named git.exe if you open a repo that contains one. No user interaction. No warning. No confirmation. Just a malicious binary in the project root, and Cursor runs it automatically. This isn’t a bug in the traditional sense. It’s a design failure rooted in a deeper delusion: that AI agents are safe because their internals are hidden. Mindgard reported this in December 2025. Cursor shipped 197 updates since. None patched it. The CISO admitted internal automation failed. The report was closed as 'informative'. Then ignored. Seven months later, the vulnerability still exists in the latest build. And here’s the real crisis: Cursor isn’t some fringe tool. It has 7 million active users. 1 million daily. 50,000 companies rely on it. This isn’t a hobbyist IDE. It’s a production system with a backdoor that opens on its own. Most AI product teams treat agent prompts as implementation details. They assume obscurity is security. They bury instructions in encrypted configs, lock down model weights, and assume attackers can’t reverse-engineer the system’s intent. Cursor’s 0day proves that’s dead wrong. The attack surface isn’t the model. It’s not the API. It’s not even the prompt itself. It’s the agent’s *expectation*. Cursor expects git to exist in the path. It expects git to be trusted. So it searches for it, in the workspace. And when it finds a file named git.exe, it executes it. Not because it’s malicious. Because it’s *what the agent was designed to find*. This is the new paradigm: if your agent’s instructions are designed to interact with the environment, then the environment becomes part of the prompt. You can’t hide that. You can’t encrypt it. You can’t obfuscate it. The moment your agent looks for files, calls binaries, or interacts with the filesystem, you’ve exposed your logic to the user’s workspace. And if your user opens a repo from an unknown source? You’ve just handed the attacker the keys. The only defense is full disclosure. Not 'we’ll patch it'. Not 'we’ll add a warning'. Not 'we’ll use AppLocker'. Those are band-aids. The real fix is to make the agent’s behavior transparent, auditable, and opt-in. Imagine a version of Cursor where: - Every external binary lookup is logged and visible in the UI - Every external execution requires explicit user approval - The agent declares its dependencies upfront: 'This project will attempt to call git, npm, and python. Confirm?' That’s not a feature. That’s the new baseline. The companies winning in AI won’t be the ones with the best models. They’ll be the ones with the most transparent agents. Alex Finn runs five local AI agents on custom hardware. He doesn’t trust cloud APIs. He doesn’t rely on black boxes. He wires Claude Code, OpenClaw, and Hermes together with Tailscale and monitors every interaction. His moat isn’t speed. It’s control. Cursor’s failure isn’t technical. It’s philosophical. They assumed security was a layer you bolt on. It’s not. It’s a property you bake in from day one. The next AI agent that treats its prompt as a secret will be the next to get owned. This isn’t about git.exe. It’s about what happens when AI agents become the new operating system. They don’t run *on* your machine. They run *with* it. And if they’re not transparent about what they’re doing, they become the most dangerous piece of software you’ve ever installed. If your agent can execute code without your consent, it’s not an assistant. It’s a trojan. The future belongs to agents that say: 'I’m about to run something. Here’s why. Here’s what it does. Do you approve?' Not because it’s safer. Because it’s the only way to build trust at scale. Cursor’s 0day wasn’t a flaw. It was a warning. And no one listened.
