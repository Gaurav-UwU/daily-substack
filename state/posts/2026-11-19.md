## The surprise in the numbers

Engineers who added AI coding assistants wrote about 30 percent more lines, yet the amount of finished work stayed flat. The Harvard working paper tracked 725,938 workers at 718 firms and found that pulling a pull request through review took 49 percent longer after the tools were adopted. The headline feels like a paradox: we are faster at drafting, but slower at delivering.

The study built its analysis on Jellyfish’s engineering telemetry, 68.3 million Jira issues, 200.9 million commits, and 49.1 million pull requests, and matched that to LinkedIn employment data from Revelio Labs. The staggered difference‑in‑differences design compares firms that adopted AI early with those that lagged, controlling for firm size. If any hidden bias exists, it would likely make AI look more productive, not less, which means the flat output result is generous to the technology.

## Review becomes the new gatekeeper

When a code draft arrives faster, the human checkpoint does not automatically speed up. Reviewers now have to parse AI‑generated patterns, verify intent, and hunt for subtle bugs that the model missed. The Harvard authors note that legal AI tools face a similar checkpoint, but they do not publish review‑stage metrics, highlighting how blind the industry is to this friction.

The HN thread on StarSling, a self‑improving CI system for agent‑volume repos, illustrates the same pressure. Contributors complained that each change runs lint, type‑checking, and unit tests multiple times, once in the agent hook and again in CI, inflating the critical path. One comment described a git‑trailer trick that let the CI skip already‑run steps, cutting build time from ten minutes to ninety seconds and reducing contention.

That anecdote shows the math of bottlenecks: three factors matter, fan‑out of non‑conflicting changes, length of the critical path, and how many times the path is executed. AI agents increase fan‑out, but without a smarter review layer the critical path lengthens, and teams end up re‑running the same checks.

## Build an AI‑augmented review layer

The first lever is to give reviewers the same AI assistance they give writers. Tools that surface likely defects, suggest test cases, and annotate generated metadata can cut the 49 percent review slowdown. Think of a “review copilot” that flags commits with missing unit coverage or suspicious similarity to existing code.

Second, restructure the CI pipeline so that the agent’s output is trusted once. The git‑trailer approach from the StarSling discussion demonstrates a concrete pattern: record which checks the agent already performed, then have the CI system skip them for intermediate pushes. Only the final merge to main runs the full suite, preserving quality while eliminating redundant work.

Third, treat review as a capacity‑planning problem. The Harvard data shows that firms with longer procurement cycles, up to a year, adopted AI later, suggesting that review tooling can be a differentiator for early adopters. Allocate headcount to build internal review bots, or partner with vendors that publish review‑stage latency.

## New metrics for a shifted workflow

Traditional velocity metrics, story points completed per sprint, no longer capture the hidden cost. Product managers should add “review cycle time” and “review‑to‑merge ratio” to their dashboards. A simple rule of thumb: if code generation time drops by more than 20 percent but review time climbs by 30 percent, overall throughput is decreasing.

Another useful signal is “AI‑authored change density”: the proportion of commits that originated from an assistant. Track this alongside defect escape rate. If the escape rate climbs as AI density rises, the review layer is under‑resourced.

Finally, experiment with a “review budget” similar to a compute budget. Set a target for maximum minutes spent in review per engineer per week, and iterate on tooling until the target is met. The Harvard paper’s 49 percent slowdown gives a baseline, aim to halve that within a quarter.

## What a PM should do on Monday

On Monday, a product manager should audit the current pipeline for duplicated checks, looking for lint, type‑check, or test steps that run both in the agent hook and in CI. Then pilot a git‑trailer or equivalent artifact that records which checks the AI already performed. Finally, introduce a review‑copilot experiment on a high‑traffic repo and measure review cycle time against a control group.

If the pilot shows a 20 percent reduction in review latency, double down and roll it out to other teams. If not, the next step is to invest in a dedicated review‑focused AI model that can surface risky patterns before a human eyes the diff.

The shift from drafting to reviewing is not a temporary hiccup; it is a structural change in the software delivery value chain. Companies that keep budgeting for more code generators while ignoring the downstream gate will see their velocity flatten. Those that treat review as a first‑class engineering problem will unlock the real promise of AI‑augmented development.
