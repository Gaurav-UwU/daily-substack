## Agents Are Already Leaking Reliability

OpenAI’s coding agents and Anthropic’s Claude Code are shipping today, yet developers still spend hours chasing silent bugs. The symptom is familiar: a model that can generate a function in seconds but fails a simple unit test that a human would write in minutes. The industry response has been to crank up model parameters or sprinkle prompt tricks, hoping the next inference will magically be correct. What we ignore is that the real cost is not compute, it is the risk of shipping broken behavior at scale.

## Dan Luu’s Test‑Driven Experiment

Dan Luu took a Rust implementation of Zstd and asked a Codex‑style model to rewrite it under twenty‑six different testing prompts. The prompts ranged from "Use test‑driven development" to "Apply QuickCheck" and even to formal methods like SMT solvers (Z3, cvc5, Yices). He also injected four pre‑packaged skills, Hegel, ECC Rust test, Trail of Bits property test, and a personal ad‑hoc skill, to see whether a ready‑made harness improves outcomes.

His predictions were modest: TDD would underperform, formal methods would not overperform, and the "Make no mistakes" instruction would do no better than no instruction. He assigned low confidence to the skill‑based conditions, noting that large skill bundles often read like tutorials rather than executable instructions. The messy graphs that resulted showed exactly what he expected, most of the testing directives failed to raise correctness above the default baseline.

The takeaway is stark: telling an agent to "use property‑based testing" does not magically give it the expertise to write effective properties. The model follows the prompt verbatim, but without a verification harness that can evaluate, mutate, and iterate, the generated tests are superficial. Dan’s data proves that naïve prompt engineering is insufficient for production‑grade reliability.

## Building a Testing Infrastructure as a Moat

If an agent cannot self‑verify, the product team must supply that capability. OpenAI’s now‑deprecated Skills catalog illustrates the direction: a repository of 1.8 k forks and 26.2 k stars that bundles instructions, scripts, and resources for agents to reuse. The catalog treats a skill as a plug‑in, installable with a single command, and reusable across projects. A disciplined team can turn that idea into a private testing harness that runs every generated artifact through differential testing, fuzzing, and mutation analysis before it reaches a user.

Such a harness creates three strategic levers. First, it reduces risk, a failed test caught in CI never becomes a customer‑visible defect. Second, it accelerates iteration, developers can trust the agent’s output and focus on higher‑level design instead of debugging. Third, it enables compliance‑first rollouts, because a verified artifact can be audited and certified without manual review. In a market where competitors race on model size, a verification layer is a non‑obvious moat that is hard to copy without the same engineering discipline.

## What Product Leaders Should Do on Monday

Stop treating agents as black boxes and start treating them as testable units. Allocate engineering time to build a repository of reusable test harnesses, think of them as the "standard library" for verification. Integrate those harnesses into your CI pipeline so that every agent‑generated commit is automatically evaluated with the same twenty‑six techniques Dan Luu explored.

Invest in internal skills similar to the OpenAI Skills catalog, but focus on the low‑level testing primitives that matter for your stack: Rust’s built‑in test framework, QuickCheck, Proptest, and fuzzers like AFL. Keep the skill bundles small and focused; Dan’s results suggest that bloated tutorials dilute effectiveness. Finally, measure the pass rate of agent‑generated code before and after the harness is in place, the data will become the moat’s KPI.

**The real moat will not be a larger model, it will be a tighter feedback loop that catches failure before it ships.**
