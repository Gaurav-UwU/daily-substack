## The leak that broke the illusion

When I opened the Hacker News thread on November 7, the headline was simple: Claude Code had slipped 1,122 real GitHub passwords into public repositories. The numbers came from Apiiro’s research, which counted 2,539 secrets across 1,994 public repos and traced 539 of those to commits authored by Claude itself.

The secret‑harvesting wasn’t a hallucination; it was a concrete file‑write bug that survived Git’s ignore logic and shipped to the world.

The offending file, `.claude/settings.local.json`, lives in the project folder. Every time a developer clicks “Yes, and don’t ask again,” Claude writes the exact command, secret included, into that JSON. The file is added to a global git‑ignore, but not to the repo’s own `.gitignore`.

If the folder later becomes a repo, or a clone is made, the file is tracked, committed, and exposed. The result is a supply‑chain leak that can’t be blamed on the language model alone.

## Why this is a supply‑chain failure

Developers already keep passwords, API tokens, and cloud keys in local config files such as `.env`. Claude Code’s “auto mode” needs those values to construct a working shell command, so it copies them verbatim. The assistant asks for permission each time, but after ten interruptions most users click the shortcut. The secret becomes a single word in a long line, invisible to the human eye.

Git’s ignore system is a defensive layer, not a guarantee. Claude adds the file to a *global* ignore list, which protects the case where the folder is never a repository. Once a repo is initialized, the global rule is ignored, and the file is treated as a tracked asset. Claude even logs that it “is tracked in the index; gitignore rules do not apply to tracked files,” yet it never warns the user.

The bug propagates automatically: 1,160 additional secrets were found in history, shared `settings.json` files, and chat transcripts saved in repos.

The same pattern appears elsewhere. A Hacker News post about ChatGPT Desktop showed that forwarding a local SSH agent to a remote machine lets the remote process push to private GitHub repos. Both incidents stem from a design choice that trades friction for convenience, and both end up leaking credentials.

## The new moat: secret‑safety as product

Historically, the competitive edge for AI coding assistants has been model size, prompt engineering, or integration depth. The Claude Code incident proves that those advantages evaporate the moment a product can exfiltrate secrets. A model can be state‑of‑the‑art, but if its runtime writes passwords into a public file, users will abandon it.

The moat now lies in three layers of secret‑safety infrastructure:

- **Real‑time secret scanning** that intercepts any command containing a known pattern before it is written to disk.
- **Repository‑aware ignore handling** that automatically adds the settings file to the repo’s `.gitignore` and refuses to commit it.
- **Telemetry that flags “don’t ask again” approvals** so the backend can audit whether a secret was stored.

Anthropic’s response on November 7 hinted at these directions. Boris Cherny said the team would prototype auto‑mode secret scanning and ensure the feature catches such leaks. The promise is not a PR‑move; it is a shift in where value is created.

## What product teams must do today

Treat every LLM‑generated snippet as untrusted code. Before you paste a Claude suggestion into a terminal, run a secret‑detection tool on the command string. Open‑source scanners like GitLeaks or TruffleHog can be hooked into the CI pipeline to catch accidental commits.

Audit your codebase for the two Claude settings files. A simple `git ls-files | grep '.claude/settings'` will surface any tracked copies. If you find them, rotate every credential listed, purge the file from history with `git filter-repo`, and add the path to both the repo’s `.gitignore` and your organization’s global ignore list.

Redesign telemetry. The assistant should emit an event every time a user selects “don’t ask again” and include a hash of the command. On the backend, reject any event that contains a secret pattern and surface a warning to the user in real time.

Finally, embed friction deliberately. The “after ten interruptions, stop asking” shortcut feels harmless, but it is the exact lever that lets secrets slip through. Replace it with a mandatory review step for any command that includes a credential‑like token. The cost of a single extra click is negligible compared to the damage of a leaked production Azure Postgres password.

## The longer view

If the industry continues to prioritize frictionless experiences, we will see more supply‑chain leaks that look like bugs but are really design flaws. The real competitive advantage will be a product that *protects* secrets by default, not one that merely *generates* code faster.

Teams that invest now in secret‑safety tooling will earn a moat that outlasts any model upgrade. Such investments pay off by reducing breach risk and building user trust. **Takeaway:** the next time you evaluate an AI coding assistant, ask not how many tokens it can process, but how it guarantees that the tokens you feed it never leave your repo.
